How I Benchmarked GitNexus, Graphify, and CodeGraph on the Same Machine

Why I Built a Benchmark Instead of Comparing Features

When I started looking at repository intelligence tools, I found that GitNexus, Graphify, and CodeGraph approach code intelligence from different directions. They all build useful representations of a codebase, but comparing them from documentation, screenshots, feature lists, or isolated benchmark numbers does not answer a very practical question: what actually happens when I run them against real repositories on the same machine?

So I decided to build my own reproducible benchmark.

The goal was not to declare a universal winner. The goal was to create a controlled baseline that I could run locally, inspect, reproduce, and eventually extend to RepoAtlas.

That distinction matters because the repositories, languages, graph structures, indexing strategies, and command semantics are different. A raw statement such as "Tool A is faster than Tool B" can easily become misleading when the underlying workloads are not equivalent.

Keeping the Three Repositories Together

I first kept the three reference repositories together under one directory called repotlas-references.

The structure is intentionally simple.

RepositoryBenchmark role
`GitNexus`GitNexus reference implementation
`graphify`Graphify reference implementation
`codegraph`CodeGraph reference implementation

This gave me a clean local boundary around the systems I wanted to compare.

I did not modify the three repositories to make them conform to each other. Instead, I inspected how each project actually works and used its own native command for the corresponding benchmark phase.

That was important because forcing every system through an artificial common command would potentially benchmark the wrapper rather than the actual implementation.

Building a Separate Benchmark Project

Instead of putting benchmark logic inside any of the three repositories, I created a separate project called repo-benchmark.

The benchmark project owns the experiment, while the three repositories remain reference subjects.

The resulting workspace looks approximately like this.

AreaPurpose
`repo-benchmark/`Independent benchmark harness
`repo-benchmark/src/`Benchmark implementation
`repo-benchmark/queries/`Planned query workload definitions
`repo-benchmark/golden/`Golden/reference data
`repo-benchmark/results/raw/`Raw benchmark output
`repo-benchmark/results/normalized/`Normalized JSON results
`repo-benchmark/results/reports/`Generated reports
`repo-benchmark/benchmark.toml`Benchmark configuration
`repo-benchmark/run.sh`Simple benchmark entry point
`repotlas-references/GitNexus/`GitNexus checkout
`repotlas-references/graphify/`Graphify checkout
`repotlas-references/codegraph/`CodeGraph checkout

The important architectural decision was separation. The benchmark harness does not become part of GitNexus, Graphify, or CodeGraph, and the tools do not know that they are being benchmarked.

Verifying the Real Commands First

Before collecting numbers, I verified the actual local versions and commands.

GitNexus was tested at version 1.6.12. For cold indexing I removed the existing .gitnexus state and ran node gitnexus/dist/cli/index.js analyze . --index-only. For warm and incremental measurements I reused the same analysis command against the existing state.

Graphify was tested at version 0.9.63. I used .venv/bin/graphify extract . --code-only. The --code-only option was important because I wanted the core benchmark to remain LLM-free and measure local code extraction rather than introduce an additional model dependency.

CodeGraph was tested at version 1.6.0. Cold initialization used node dist/bin/codegraph.js init -y ., while warm and incremental measurements used node dist/bin/codegraph.js sync . against the existing .codegraph state.

ToolVersionCold operationWarm / incremental operation
GitNexus1.6.12`analyze . --index-only` after removing `.gitnexus``analyze . --index-only`
Graphify0.9.63`extract . --code-only` after removing output`extract . --code-only`
CodeGraph1.6.0`init -y .` after removing `.codegraph``sync .`

I also deliberately avoided GitNexus --force because that mode could reuse parser output and would therefore change what the cold measurement represented.

For Graphify, I did not use update . as the incremental benchmark because the observed behavior re-extracts every code file. I wanted the incremental command to represent the tool's existing synchronization behavior instead.

Making the Core Benchmark LLM-Free

One of the most important decisions was to keep the core benchmark independent of an LLM.

The benchmark therefore measures repository processing rather than agent behavior. Ollama is intentionally reserved for a separate future benchmark where I can evaluate how well an agent uses the generated repository intelligence.

This separation prevents indexing performance, retrieval performance, model quality, token usage, and agent behavior from becoming one confusing metric.

Three Benchmark Phases

I divided the benchmark into three primary phases: cold, warm, and incremental.

Cold means starting without the tool's existing repository index or state. This measures the initial repository analysis or graph construction path.

Warm means running the tool again when its existing state is already present. This measures what happens when the repository has already been processed.

Incremental means making a controlled change to one tracked source file, running the tool, and then restoring the file byte-for-byte. This provides an initial measurement of how the tools behave when the repository changes.

Each phase used one warmup followed by three measured runs.

PhaseMeaning
ColdFresh repository analysis/index construction
WarmExisting index/state already present
IncrementalControlled tracked-file modification followed by synchronization
WarmupOne non-measured run
MeasurementsThree measured runs per tool and phase

The benchmark recorded wall-clock time, CPU time, and peak resident memory.

The Repositories Were Not the Same Size

One of the first things the benchmark made obvious is that these repositories are not equivalent workloads.

The source census showed the following.

ToolSource filesSource LOCTotal files
GitNexus4,7653,501,0906,305
CodeGraph7132,352,9441,101
Graphify445169,7661,467

GitNexus contains the largest number of source files and the largest source LOC count in this baseline.

CodeGraph has substantially fewer source files than GitNexus but still contains more than 2.35 million source LOC.

Graphify is much smaller in source LOC than the other two.

That immediately made one thing clear: raw wall-clock time cannot be treated as a fair universal ranking. I therefore included LOC-normalized diagnostics, while explicitly treating them as diagnostics rather than definitive throughput measurements.

The CPU increase in the outlier was much smaller than the wall-clock increase. With only three measured runs, I am not attributing a cause to that behavior. Instead, I treat it as an observed outlier and use the median rather than the mean as the primary statistic.

Graphify was extremely consistent during cold indexing.

CodeGraph was also very consistent, although its cold memory footprint was considerably larger than Graphify's.

Warm Benchmark Results

The warm phase produced a very different picture.

ToolMedian wallMedian CPUMax RSS
GitNexus17.503 s30.295 s2,554.1 MB
Graphify4.787 s7.552 s262.0 MB
CodeGraph0.352 s0.254 s106.6 MB

The measured CodeGraph warm operation was sub-second on this workload.

GitNexus remained in the multi-second range, while Graphify completed in under five seconds.

Again, this is a measurement of the particular commands and repositories used here. It should not be interpreted as a universal statement about the underlying tools.

Incremental Benchmark Results

The incremental phase was designed around a controlled source-file modification.

The harness modifies a tracked source file with a unique comment, executes the tool's incremental/warm synchronization command, and then restores the file byte-for-byte.

The measured results were:

ToolMedian wallMedian CPUMax RSS
GitNexus26.060 s45.388 s3,596.2 MB
Graphify4.837 s7.625 s264.7 MB
CodeGraph0.462 s0.346 s123.2 MB

CodeGraph's measured incremental operation was again sub-second.

GitNexus and Graphify both completed successfully but required substantially more elapsed time on this workload.

The important caveat is that this experiment does not yet prove exactly how much of the repository each tool reparses or how dependency propagation differs internally. That requires a more detailed incremental workload and instrumentation.

Memory Was Another Clear Dimension

Performance is not just elapsed time.

The cold peak RSS measurements showed a significant difference between the three tools.

ToolCold peak RSSWarm peak RSSIncremental peak RSS
GitNexus6.18 GB2.55 GB3.60 GB
Graphify0.60 GB0.26 GB0.26 GB
CodeGraph3.42 GB0.11 GB0.12 GB

Graphify had the lowest observed memory footprint in all three phases.

GitNexus had the highest observed peak RSS in the cold benchmark.

CodeGraph had a relatively large cold initialization footprint but a very small warm and incremental footprint.

The benchmark currently measures peak resident memory as the largest observed single process, rather than summing the complete process tree. That limitation is important and is one of the areas I want to improve in the next version.

What I Found Most Interesting

The first major observation was that the three tools exhibit very different execution profiles.

GitNexus showed substantial cold processing time, substantial CPU usage, and the largest observed memory footprint. Its cold benchmark also showed a clear timing outlier.

Graphify was remarkably consistent and had the smallest observed memory footprint.

CodeGraph showed a large cold initialization footprint but extremely short warm and incremental operations on this workload.

The second major observation was that cold performance tells only part of the story. Once state exists, the execution characteristics change significantly.

The third observation was that reproducibility matters. Without running the same commands multiple times, I could easily have mistaken a single GitNexus cold run for representative behavior.

What I Am Not Claiming

I am deliberately not saying that one of these tools is universally faster.

The repositories are different sizes. The implementations have different semantics. The benchmark commands do different amounts of work. The sample size is still small.

What I can say is that on this specific local workload and these exact benchmark commands, the measured behavior was materially different across GitNexus, Graphify, and CodeGraph.

That is a much more useful starting point than an unsupported general ranking.

The Current Benchmark Limitations

The benchmark currently has three measured runs per phase, which is enough to expose obvious behavior but not enough for strong statistical conclusions.

The repositories also differ in language composition, source volume, file distribution, graph structure, and implementation architecture.

The process monitor samples the process tree, so very short-lived child processes can potentially be missed. Peak RSS currently represents the largest observed single process rather than the sum of all processes.

The current benchmark also does not yet measure query latency, semantic graph correctness, failure recovery, restart determinism, worker-count scaling, or end-to-end agent effectiveness.

Those are separate dimensions that need their own controlled experiments.

Why I Kept RepoAtlas Out of This First Baseline

RepoAtlas is the system I ultimately want to evaluate alongside these projects.

But I intentionally did not add it to this first benchmark.

I wanted to establish a baseline methodology first rather than changing the methodology to fit RepoAtlas after seeing the numbers.

The idea is simple: define the benchmark, validate the commands, collect the baseline, document the limitations, and only then introduce RepoAtlas as another implementation under the same rules.

That should make the eventual comparison much easier to reason about.

What I Want to Benchmark Next

The next version needs to go beyond a single repository per tool.

I want small, medium, large, and enterprise-scale repository tiers, more measured repetitions, controlled worker-count sweeps, better process-tree resource accounting, query latency, query correctness, graph correctness, and multiple types of incremental changes.

Separating Engine Benchmarks from Agent Benchmarks

I also want to keep another distinction clear.

An indexing engine can be fast while an agent built on top of it can still perform poorly. Conversely, a repository intelligence system might provide more useful context to an agent even if its raw indexing time is not the lowest.

That is why I plan to keep the Ollama-based agent benchmark separate.

The agent benchmark can evaluate tool calls, task correctness, evidence quality, completeness, unsupported claims, token consumption, and end-to-end latency without contaminating the core repository-processing measurements.

The Bigger Goal

This benchmark is not really about producing a leaderboard.

It is about creating an evidence layer for repository intelligence.

GitNexus, Graphify, and CodeGraph each provide different approaches to understanding source code. By putting their repositories in one controlled workspace and building an independent benchmark harness around them, I now have a repeatable way to measure what happens on my machine rather than relying only on feature descriptions.

The benchmark results are now stored as normalized JSON, with the intention of generating formal reports from those results.

The complete benchmark analysis and tables can be included alongside this article as the detailed technical report.

Final Takeaway

The most useful result of this experiment was not a single number.

It was the benchmark itself.

I now have one independent project that can run controlled cold, warm, and incremental experiments against GitNexus, Graphify, and CodeGraph, record wall time, CPU time, and memory, preserve the raw and normalized results, and provide a foundation for deeper experiments.

The next step is to bring RepoAtlas into that environment only after the methodology is mature enough to make the comparison meaningful.

That is how I want to approach repository intelligence: not by asking which tool sounds better, but by building reproducible experiments and collecting evidence.

Reproducibility

The benchmark was designed as a standalone project with a simple entry point:

./run.sh benchmark

The benchmark stores normalized results under:

results/normalized/
├── census.json
├── cold.json
├── warm.json
└── incremental.json

The detailed analysis, methodology, raw measurements, normalized diagnostics, limitations, and future benchmark plan are maintained as Markdown documentation alongside the benchmark project.
